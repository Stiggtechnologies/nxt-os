# Company journal import contract

This lane publishes a normalized, company-isolated journal and trial balance. It does not activate financial cutover, change the original source, seed the legacy Ledger, reconstruct missing transactions, or infer subledger allocations. Source identity/currency flags and reviewer labels are operator assertions under the existing shared workspace key.

All routes require the existing admin bearer and return private/no-store responses. Upload `Chunk` objects to `POST /api/company-books/{company}/chunks`, then pass the returned SHA-256 references into `POST /{company}/imports/preview`. The exact Rust models are in `models.rs`. Amounts are canonical nonnegative decimal **cents strings**, never floating point. Native account classifications may be null. Journal source row identities must be unique within the submitted report. Explicit valued zero rows are retained; missing source amounts must be blocked by the source adapter, not converted to zero.

Each entry and line may include `source_metadata`, an original bounded JSON object (16 KiB, depth 8, 1,000 nodes). Preserve source transaction type, number, name, original cell presence/types/values/formulas and original worksheet/report references there. It is part of the immutable chunk hash. The separately retained original report/archive hashes remain the byte provenance; normalized JSON is not claimed to reproduce original spreadsheet bytes.

Preview freezes the complete submitted chunk list, source archive/report hashes, claimed date coverage, currency/identity assertions and per-account trial balance controls. It recomputes every journal entry balance and every account control using checked integer arithmetic. Unknown identity/currency, incomplete history, unbalanced entries or missing/mismatching controls prevent commit. Account classification completeness is reported separately; it is not a claim that P&L/BS or other classified reports have been implemented. Preview request IDs are content-bound: reuse with a changed payload returns 409.

Each trial balance control requires a basis: `source_report_row` pins its actual positive TB row and TB report hash; `derived_zero_journal_omission` has no TB row and pins the Journal hash, submitted account row count, and cumulative Journal debit/credit proof. The latter is accepted only for an exact proven zero net. Analysis reports independent TB matches separately from derived zero controls. Neither implies a complete chart of accounts; Journal and TB exports do not list every unused account.

`POST /{company}/imports/commit` takes `{preview_id, expected_head:null, request_id, reviewer_label}`. The first import requires an empty company head. The service writes hash-addressed immutable receipt content before one CAS publishes its hash as the company head. No reader resolves staging chunks without that published head. Interruption before CAS leaves invisible staging; interruption after CAS is recoverable by the same request. An exact retry returns the same receipt; competing requests or a changed request payload return 409. A second full-history import is rejected, even when its rows look similar: a separately reviewed delta/replacement protocol is required to avoid double posting.

GET `/{company}`, `/{company}/imports/{preview_id}`, `/{company}/entries?offset=0&limit=100`, `/{company}/register/{account_id}?offset=0&limit=100`, and `/{company}/trial-balance` resolve and hash-check the published receipt, preview and all referenced chunks. Readers fail closed on corruption or absent committed references. Register order is explicitly immutable source order, with a signed exact-cents running balance; it is not silently reordered by date. Pagination limits are 1–200 rows.

Inventory GET `/api/company-books?offset=0&limit=25` is separately bounded to 1–50 companies per page and returns total/has_more. Its batched receipt/preview metadata checks are explicitly marked `metadata_only`; complete chunk/history checks happen on book detail/read/write routes. Inventory heads and preview histories are truncated summaries, never a financial readiness or recovery result. Full source inventory lives at the separately versioned `/roster` endpoint and does not imply any financial import.

Initial bounds: 512 KiB per chunk; 24 MiB referenced journal; 256 chunks; 20,000 accounts; 100,000 entries; 500,000 lines; 20,000 lines per entry. Source adapters must preserve complete groups or reject oversized groups rather than omit lines.

Native operations use `POST /{company}/journals`, `POST /{company}/journals/{entry_id}/reverse` and `POST /{company}/period-lock`. They require the exact current head, request ID and operator label. Journal amounts are positive, balanced exact cents; lines reference only accounts in this company. Reversal appends the exact opposite of a recorded entry and never changes the original. A target may have only one recorded reversal. Period locks advance monotonically; no unlock route exists. Backdated operations into a locked period fail. Native records carry explicit `native_adjustment` provenance and source_row 0, never a fabricated source row.

Head/v2 appends hash-addressed operation receipts linked to the prior head. One CAS publishes each operation. Exact retries return the original operation receipt even after later activity, with `current_head_sha256` when appropriate; changed request content or concurrent stale heads return 409. The validator projects all journal/reversal/lock operations and checks cumulative journal references, lock progression and source baseline binding. Native limits are 128 operations, 4 MiB cumulative journal content, 500 lines and 256 KiB per adjustment. The trial balance exposes combined books, immutable `source_baseline_analysis`, `native_delta`, and explicit whether combined balances still match the source baseline. This does not synchronize changes back to QuickBooks.

Typed customers/suppliers, open AR/AP allocation, invoices/bills/payment states, bank reconciliation, attachments, tax/payroll, permissions and source delta synchronization are not inferred from journal descriptions. Those capabilities and independently approved recovery/reconciliation gates remain prerequisites to a full operational cutover.
