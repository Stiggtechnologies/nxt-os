# Parallel-test review runbook

Checkpoint: 2026-10-26. The user explicitly authorized preserving the selected source exports **as-is in parallel test mode**, including publication of protected read-only snapshots for review in NXT. QuickBooks and the other original applications remain the source of truth until a separate, fully evidenced cutover decision. The new Migrations implementation and local verification do not establish that its production release or any real snapshot publication has completed; bind those claims to actual release and private publication evidence when available.

This permission covers source acquisition, exact archive preservation, immutable snapshot publication and review. It grants no Ledger posting, source write-back, automatic synchronization, payment, filing, source freeze, authority switch, source retirement or record deletion. A snapshot containing unresolved source amounts can be accepted as a faithful review copy while its financial assessment and live migration remain blocked. The G0–G7 gates and rollback controls in [CUTOVER_PLAN.md](CUTOVER_PLAN.md) remain in force for live acceptance.

## Prepare each company separately

1. Maintain a private cohort register binding the authorized source company/realm to its cohort token, operator, acquisition, reporting settings and exact source archive SHA-256. Keep real company names, source amounts/counts, source filenames containing identifiers, raw cells, private paths and receipts outside Git. Repository examples and tests use synthetic data only.
2. Preserve the original exported ZIP byte-for-byte before processing. Retain it in the approved private evidence location together with its size/hash, acquisition method, source settings and any known omissions. A report ZIP does not establish completeness of attachments, nonposting records, audit history, source IDs, lists or the recoverable source company.
3. Prepare a new pack with [SHADOW_SNAPSHOTS.md](SHADOW_SNAPSHOTS.md). Use one company and acquisition per pack. Confirm the selected report headings against the intended company; heading equality is an accidental-mix check, not verified legal identity. Do not replace old source artifacts, packs or assessments.
4. Record the fresh immutable snapshot ID and manifest/source hashes in the private register. Each company has separate snapshot IDs; a later acquisition or changed manifest requires a new ID. The server rejects a different manifest under an existing ID. An identical retry is a replay of the same snapshot, not a new acquisition.
5. Inspect the preparation receipt and manifest before upload: `mode: parallel_test`, `source_of_truth: original_system`, source system, company/cohort binding, all referenced chunks, selected reports, exceptions and explicit limitations. Confirm preparation and deployed publication limits agree and that the complete supplied artifact fits. Do not omit rows, exception evidence or archive members to fit a limit.

`captured_at` describes acquisition metadata. When inferred from a local file's modification time it must remain disclosed as such. `cutoff_date` is a requested label, **not a row filter, consistent high-water mark or proof that source writes were frozen**. Reports containing all-dates rows retain those rows. The original applications continue their normal authoritative operation during this parallel test; later changes require another acquisition, not an assumed live sync.

## Publish only to the selected protected review destination

Confirm the exact candidate commit/build, origin, durable backend and namespace through authenticated status/readback evidence before using a real pack. Keep credentials out of commands, logs, Git and receipts. The current shared workspace key protects these endpoints but does not verify individual identities, company membership or separation of duties. Record the intended operator/reviewer access privately and disclose this limitation; snapshot publication does not close the live IAM gate.

The explicit publisher is `scripts/publish-shadow-snapshot.mjs`; it accepts a selected private pack, destination origin and a new private receipt path. It obtains its credential only through `NXT_SHADOW_KEY`. Uploads go to `/api/migrations/chunks`; publication goes to `/api/migrations/snapshots`. These are target review-store writes. They do not call a Ledger import or posting route and do not change the source system.

Publication validates the declared snapshot contract, content hashes, archive reconstruction, row-part bindings, ordering, bounds and exception row references before adding a catalog entry. It does not independently parse the archived XLSX or prove every extracted row equals that source. Chunks are content-addressed and immutable. A partially interrupted chunk upload is not a published snapshot. Retry the same verified pack; do not modify it or delete shared content to recover. A catalog conflict, invalid content, missing chunk, storage error or capacity rejection requires investigation and a retained private failure record.

After publication, record the returned snapshot ID, server manifest hash and publication timestamp. Preserve the local exact manifest-byte hash separately: server manifest serialization is not a promise of identical JSON byte order. The publisher compares manifest content and verifies the full downloaded archive's size/SHA-256 plus targeted report rows. Its receipt is evidence of those specific requests and checks, not a complete report-row comparison, verified reviewer approval, general no-change proof or source completeness certification.

## Review and test with the nominated reviewer

The user-nominated reviewer is the intended parallel-test participant. The manifest's `reviewer_label` is responsibility metadata only. It is not an authenticated sign-off by that person and must not appear as financial approval. Keep the actual identity, availability, access arrangement and review notes in the private register. Independent verified preparer/reviewer principals remain required for live acceptance.

1. Open the Migrations review surface and select the private cohort/snapshot ID. Confirm the company, source, acquisition/cutoff labels and original-system authority banner against the private register. Do not select solely by a display name.
2. Inspect every selected report and its original worksheet row/column references. Page through all rows for a complete review; the publisher's targeted first/last/exception-row checks alone do not prove every parsed row equals the XLSX. Record the reviewed coverage and any gaps.
3. Compare the source reports with preserved raw values, formulas/caches and supplementary cents. Keep absent cells, blank cells and literal zero distinct. A blank debit/credit, unsupported formula or unresolved subtotal remains explicit evidence; do not infer zero, void or nonposting status, adjust a balancing entry or overwrite the source expression to obtain a pass.
4. Review every disclosed exception and limitation, classify the accounting/source-workflow question and record its owner. An unresolved exception may remain in an as-is snapshot. It continues to block any dependent financial acceptance until separately resolved from source evidence.
5. Download the original ZIP and independently verify its exact SHA-256 against the private acquisition register. Retrieve required source reports using the supported source software. Preserve a separate readable archive and restore/retrieval evidence where needed; retaining this ZIP alone does not complete the statutory records or disaster recovery controls.
6. Exercise intended read-only navigation/report/download behavior and document missing or unsupported workflows. Expanded navigation labels and links do not establish implemented capability or QuickBooks/other-product parity. Compare actual behavior with the required-case inventory.
7. Record findings tied to the immutable snapshot ID, source archive hash, exact application build and review date. Distinguish review-copy fidelity, native feature behavior, source reconciliation and final financial acceptance. A reviewer label or completed UI walkthrough closes none of the latter gates by itself.

For each private publication, retain status/authentication evidence, preparation/publication receipts, exact archive readback, report comparison coverage and the exception register. Where claiming unchanged native books, compare authorized before/after Ledger evidence; a publisher counter stating zero requested posts is not an independent whole-system state comparison. Do not publish client evidence in issue bodies, screenshots, test fixtures or Git history.

## Stop, recover and advance

Stop publication/review for wrong-company bindings, changed local content, archive/hash mismatch, missing or truncated rows, unexpected access, unresolved target state, failed durable storage/readback or exceeded capacity. Preserve the source, old snapshot IDs and evidence. Return staff to the authoritative source workflow while investigating. There is no snapshot delete or in-place edit workflow; corrections are new acquisitions and new IDs. Orphan cleanup or production recovery requires a separately reviewed path that preserves unrelated data.

No financial reversal is needed merely to stop a read-only review copy because it has not posted native books. If an unexpected business write is detected, invoke the incident and post-write recovery procedures in [CUTOVER_PLAN.md](CUTOVER_PLAN.md); a code rollback does not undo data effects.

Before any live cohort GO, complete source inventory/completeness, currency/basis and cutoff/freeze evidence; verified identities/company IAM; source-specific staged importer and mappings; full reconciliation and required-case coverage; capacity/retention controls; two rehearsals including interruption and measured restore/reverse-delta recovery; independent review; and an exact cohort decision. Scheduled backup observation, notification drill and independent off-device key custody remain separate evidence requirements. Continue source use and certified filing throughout the parallel test.
