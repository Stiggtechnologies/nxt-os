# Family workspace

Families & PLAN links two existing T1 workpapers for the same tax year and the same literal workspace/client reference. Firm workspace links unassigned workpapers; selecting a company shows its workpapers using the existing company selector alias contract. Aliases are used for viewing only: both selected returns must still have the same literal stored client reference, which is preserved unchanged. Linking is explicit comparison membership, not a legal-identity determination. The new endpoints require verified staff permission for both members. Scoped preparers can compare and update pairs assigned to their client reference; read-only staff can compare without mutation controls. Scoped staff cannot access unassigned returns. Collections filter each candidate and both family members before producing response arrays, so hidden names, counts and fingerprints are not returned.

Open a family to compare every saved input side by side, follow each individual return, and update the family label/members. Membership updates require both selected return revisions plus a family SHA fingerprint. A monotonically increasing family revision prevents an away-and-back label/member change from restoring an old fingerprint. Legacy families default to revision zero and omit it when serialized; old saved bytes remain unchanged until an explicit update.

Verified 2025 entry schemas permit manual paired input entry. Saving both returns uses one TaxState compare-and-swap: validate both member IDs, same year/company, exclusive membership, family fingerprint, return revisions, editable status, known field/type/bounds and both input documents before changing either. Verified actor write policy, expected client reference and both old/new member assignments are checked again inside that same compare-and-swap. If either side fails, neither side nor audit changes. Both revisions/input revisions advance; status becomes draft; current calculations, reviews and preparer sign-offs are invalidated. Existing history arrays remain exact. Legacy current snapshots/reviews absent from arrays are preserved there before invalidation, subject to existing limits. Other fields are cloned, including future grouped-slip fields.

Grouped-slip authoritative values cannot be overridden through paired editing. The compatibility guard detects serialized `slip_groups`, uses the existing slip aggregator, and rejects a proposed value that differs for any managed key. Occurrences must be edited in the individual return. Fields absent from the accepted browser schema, unsupported years, unknown statuses, filed records and locked returns remain read-only. No unsupported input is silently deleted and a saved field cannot be removed through this simpler editor.

The browser rejects stale routes, detached forms and workspace changes including roundtrips. It keeps separate dirty membership/paired-input states so one form cannot silently discard the other. Normal tax navigation supplies the existing unsaved-change prompt. No automatic calculation, approval, filing, source mapping or client-profile update occurs.

## PLAN gap

Automatic application of existing spouse proposals is deliberately unavailable. The optimizer returns proposals rather than a typed paired-change contract, and some results have null deltas. Its helper now rejects unsupported calculations and review-blocking diagnostics before reading a tax total: partial totals cannot masquerade as calculated savings. A regression covers the unverified T1032 case. Supported computed proposals still do not establish current saved snapshots or a verified paired election contract; a positive displayed saving is insufficient authority to mutate both returns.

The CRA requires a joint election for eligible pension splitting, with related amounts and credits reconciled on both returns ([pension splitting](https://www.canada.ca/en/revenue-agency/services/tax/individuals/topics/pension-income-splitting.html), [T1032](https://www.canada.ca/en/revenue-agency/services/forms-publications/forms/t1032.html)). Medical expense eligibility and the chosen claim period also require evidence ([CRA eligible medical expenses](https://www.canada.ca/en/revenue-agency/services/tax/individuals/topics/about-your-tax-return/tax-return/completing-a-tax-return/deductions-credits-expenses/lines-33099-33199-eligible-medical-expenses-you-claim-on-your-tax-return.html)). This workflow adds no financial election rule. Closing this gap requires year-specific typed deltas, eligibility/election evidence, current paired input/output hashes, supported calculations/diagnostics, provincial effects and independent tax-rule tests before an atomic apply endpoint is exposed.

## Validation

`cargo test --locked --test tax_family_workspace` checks stale and cross-company/year/member rejection, whole-state equality after failure, atomic paired changes, history preservation, legacy serialization, family revision roundtrips, locked/unsupported/unknown-field holds, and actual MFA-authenticated scoped preparer/read-only access: A pairs succeed, B/mixed/unassigned pairs are denied, hidden fields stay absent, read-only writes fail, and a member scope change is rechecked in the service CAS. The library grouped-input guard test covers conflicting derived values.

`node --test tests/tax_family_workspace.test.mjs` runs actual family handlers with synthetic records, including one paired request, false flags, workspace roundtrips, detached forms, competing dirty forms and unknown catalog readiness. An isolated browser proof uses synthetic records only and blocks all network; it exercises actual paired controls and desktop/mobile layout. Integration with grouped slips must retain the exact aggregator assertion. This is a bounded family workflow, not full DT Max parity.
