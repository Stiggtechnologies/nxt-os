## Financial model and review readiness

Money is integer **CAD cents**. Accounts have stable engagement-local IDs, codes/names, one of `asset`, `liability`, `equity`, `revenue`, `expense`, optional group mapping and current/prior debit/credit columns. A positive balance is one-sided; negative amounts or simultaneous positive debit and credit are rejected. Zero-balance accounts remain visible and require mapping before supported review.

Groups have original codes/names and a matching account kind. Optional four-digit GIFI codes are **detail metadata**, not proof of a validated taxonomy, generated return or export compatibility. Aggregate GIFI total codes cannot be used as detail mappings; tax provision metadata is limited to expense groups.

Local entries support `adjusting` and `reclassifying`. Both affect this module's working/report basis; neither writes NXT Ledger. Every adjustment requires valid in-period dates and existing account references. Incomplete, zero-line or unbalanced entries block review, even when another bad entry offsets their aggregate difference. Source Caseware's full journal/balance-type semantics are not reproduced by these two local labels.

Analysis returns:

- Unadjusted, adjustment and adjusted debit/credit totals and differences, comparative totals/difference and unmapped-account count.
- Account-level base, adjustment, adjusted and prior balances, with debit/credit normalization preserving contra signs.
- Group current/prior totals, basic current/prior financial summaries and explicit diagnostics/readiness.

The statements summarize assets, liabilities, equity, revenue, expenses, net income and a balance-sheet difference. They are internal workpaper summaries, not a complete set of standards-compliant financial statements or CaseView-generated disclosures.

Current/prior periods must be real canonical dates from 1900 through 2200, each containing 1â€“366 inclusive days. Prior dates are supplied together and must end before the current period begins. Nonzero comparatives without prior dates block review. Empty TB, unmapped accounts, blank required workpaper evidence, unbalanced financial data and unresolved blocking issues also prevent supported review.

The synthetic acceptance fixture starts with debit and credit totals of 2,400,000 cents. An accrued expense/payable entry of 100,000 cents produces adjusted totals of 2,500,000 cents, assets 1,700,000, liabilities 400,000, equity 1,200,000, revenue 900,000, expenses 800,000 and net income 100,000. These are independent NXT checks; no Caseware calculation was run for this fixture.

## Workpapers, issues and human review

A workpaper has a stable ID/reference, title, folder label, evidence text, required flag, account/adjustment references and prerequisite workpapers. References must exist, be unique within each list and form an acyclic dependency graph. Folder labels organize workpapers; they do not create filesystem paths. Bounded opaque file versions are documented below. Scalable attachment storage, Office/CaseView execution, tickmark graphics and a linked-document calculation engine remain separate capabilities.

### Manual text and placeholder workpapers, local implementation checkpoint

The original NXT document type is `manual` (plain text with optional bounded opaque files) or `placeholder` (pending planning material). Manual is the default and is omitted from serialization, preserving legacy workpaper input and snapshot preimages. Unknown types and explicit null types are rejected. Neither type interprets a proprietary Caseware, Office or CaseView document.

A placeholder retains its stable ID, reference, title, folder, required flag and planning references/dependencies, while its body must contain exactly zero bytes and it cannot carry annotations or file versions. A required placeholder produces a blocking pending diagnostic; an optional placeholder produces a nonblocking pending diagnostic. Neither can receive a sign-off or direct file upload. An optional placeholder can still prevent a dependent workpaper's checkpoint under the existing dependency rules. Convert it to manual text before adding evidence. These are NXT review policies, not recovered vendor rules.

Conversion uses the normal revision-checked workpaper save on the same ID, retaining issue/dependency references. Converting a manual paper to a placeholder requires its existing body and annotations to be explicitly cleared/removed and saved first. A paper with retained immutable file versions must remain manual; create a separate placeholder rather than dropping those versions. Type conversion does not silently discard evidence or retain old approvals: saving invalidates the active calculation/sign-offs under the existing history controls. Locked and archived engagements remain read-only.

Native snapshots, JSON/ZIP packages and escaped print retain the type; print labels placeholders as pending material rather than evidence. Comparative rollforward retains document types and planning links while clearing current evidence and approvals, and its origin retains the exact prior snapshot. The copy policy adds the type-preservation declaration only when a source placeholder exists, preserving the legacy empty-type policy. Earlier readers reject stored placeholder fields; use a compatible reader or a forward fix after adoption, without deleting evidence to make an older reader load.

This first checkpoint describes the original type contract; the subsequent deployed acceptance is recorded below. The source-format, full document-manager, Office/CaseView, scalable retention, verified identity and paired source-workflow gaps remain open.

### Account-context annotations

An original NXT account mark binds both the exact manual workpaper text and a referenced account's saved local context. It is an ordinary fixed or custom text annotation with an appended optional `account_anchor` object containing `engagement_id`, `account_id` and lowercase `context_sha256`. The account must exist and be referenced by that manual workpaper. Placeholders cannot receive marks. Missing account anchors preserve the existing text-only serialization and behavior; present null, sequence, unknown-key and malformed anchor values are rejected.

The context is SHA-256 of compact sorted-key UTF-8 JSON, version `nxt-account-annotation-context/v1`. It includes the actual owning engagement ID, native ruleset, currency/current/prior period dates, workpaper ID/reference, complete selected Account input, its linked Group definition or null, and complete touching local Adjustment objects in their saved entry/line order, including counterpart lines. It excludes annotations, unrelated accounts/workpaper text, group aggregate balances and external Ledger/Tax state. The workpaper text binds separately through the existing `body_sha256`. This is a defined NXT input-context check, not proof of a procedure, certified balance, authenticated operator or Caseware behavior.

Account-context or text changes produce blocking diagnostics until the mark is reviewed and replaced. Existing annotation IDs cannot add/remove/change account scope or re-anchor its text while account-scoped; removal and a new ID are required. A server-owned lifetime receipt reserves each observed ID, including removed marks and legacy body-only IDs encountered during a save. An account receipt hashes owner, paper, ID, kind, copied custom meaning, account anchor and text hash. Restoring the exact binding is allowed; reusing a removed ID with a changed binding or converting a reserved body-only ID into an account mark is rejected. Body-only edits retain their existing behavior. These receipts enforce local consistency, not authenticated authorship or tamper-proof evidence.

Other saved changes continue to invalidate active calculation/sign-offs. Actual owner IDs are checked on save and across stored current, historical and rollforward-origin documents. The target registry covers its own documents/history; an embedded rollforward origin retains its separate source owner. The original NXT lifetime registry limit is 2,000 IDs per engagement; reaching it rejects a save without partial persistence. Existing active annotation/history/request capacities remain unchanged, and receipts count toward existing record/workspace byte limits. Receipts are server record metadata, outside annotation/input hash preimages; absent/empty legacy metadata remains omitted. New saves can adopt receipts even when all marks are body-only.

`GET /api/engagements/{id}/workpapers/{paper}/account-anchors` is authenticated and returns `private, no-store` saved options without mutation or financial values. Format `nxt-account-annotation-options/v1` binds owner, saved revision/input revision, input hash, paper ID/body hash and each referenced account's context digest. The two-stage browser picker bounds workpaper and account choices by existing collection limits. It checks the saved owner/revisions/body/reference set and guards the full local saved draft across both dialogs, the GET and hashing; it does not pretend sorted browser JSON reproduces a Rust typed input hash.

Snapshots and native JSON/ZIP packages retain copied anchors; full record exports retain lifetime receipts. Escaped print identifies the saved target ID/context digest; current account labels do not reconstruct historical values. Comparative rollforward clears active marks and starts an empty target registry while retaining the exact original source snapshot. After any registry adoption, recovery requires a compatible reader or forward fix. Older readers reject account-anchor fields but may silently discard registry-only metadata after marks are removed, so an older binary is not a safe rollback. The release evidence below covers this native slice. Graphics, line/cell/PDF/image targets, source formats, verified identity and paired source behavior remain open.

### Selected-text range contract, local checkpoint

The next original NXT slice targets a nonempty selected range within a saved manual text workpaper. An appended optional `text_range_anchor` contains the actual owning `engagement_id`, inclusive `start_utf8_byte`, exclusive `end_utf8_byte`, exact copied `selected_text` and lowercase `selection_sha256`. The existing complete `body_sha256` remains required. A mark has either account scope or selected-text scope; the two cannot be combined. Placeholders cannot receive marks. Offsets remain within the existing 16,384-byte workpaper bound; the recorded selection is limited to 4,096 UTF-8 bytes. Copy length, hash and permitted text controls are checked. Present null/array/unknown/missing/duplicate fields and malformed offsets are rejected; absent fields retain legacy hash preimages.

When the whole-body hash matches, the server also checks original UTF-8 character boundaries and exact equality between the selected original slice and its copy. When text changes, the bounded copied selection remains recorded evidence and the existing stale-text diagnostic blocks review. An old offset is never applied to the changed body to reconstruct evidence. The copy and hash are local consistency controls, not proof of source authenticity, a completed procedure or verified individual attribution.

The browser first chooses a saved nonempty manual paper, then uses a native selection in a read-only text box. It maps normalized CRLF/CR display text and UTF-16 selection positions back to the original saved text's UTF-8 boundaries, rejects split surrogate positions and preserves the original selected bytes. Saved owner/revisions/full input preimages, target, selection and custom definition are guarded across dialogs and hashing. Recorded copies are escaped in display and print and identified as recorded text. Existing body-only and account-mark workflows retain their contracts.

The existing server lifetime registry appends an omitted optional `text_range_binding_sha256`. A receipt cannot contain both account and text-range digests; a body-only reservation contains neither. The new range digest binds owner, paper, annotation ID, kind, copied custom definition, complete range anchor and body hash under `nxt-text-range-annotation-binding/v1`. Existing account digests remain byte-for-byte unchanged. Removed IDs cannot change scope or binding; exact restoration is allowed. The existing 2,000-ID, annotation, history and byte limits still apply. Current/owned-history receipts and separate source-origin ownership remain enforced; rollforward clears active marks and starts an empty target registry while preserving source evidence. Compatible readers or a forward fix are required after receipt adoption.

Deployment, rendered native selection and persistence acceptance remain separate gates at this checkpoint. This is not a recovered Caseware line/column schema, a PDF/Office/cell annotation or paired source-runtime parity.

Issues can reference a workpaper and carry title/detail, priority (`low`, `medium`, `high`), blocking flag, state (`open`, `resolved`), resolution and carry-forward preference. Resolving an issue requires an explanation. Blocking open issues prevent supported review; the issue record is evidence, not a message delivered to anyone.

The implemented initial lifecycle uses saved revisions, immutable input/result snapshots, `prepared`/`reviewed` document sign-offs and engagement states `draft`, `in_review`, `locked`, `archived`. Preparation occurs in draft; review occurs in `in_review`, after preparation. Dependency workpapers need their checkpoint at the same stage. At least one required workpaper and all required preparations/reviews precede the corresponding transitions; a fresh supported calculation precedes review and locking. Archive requires a locked source. Transitions and sign-offs require operator and note. Reopening to draft invalidates active calculation/sign-offs while preserving history; editing also invalidates them. These are internal controls, not professional-standard assurance or verified individual authority.

The inherited workspace uses a **shared admin key**. Operator/preparer/reviewer strings are responsibility labels, not verified individual identities or enforceable separation of duties. This initial module cannot be presented as company-isolated IAM or an independently authorized assurance-review system. Original NXT hard gates are policy choices; Caseware's documented protected/unprotected sign-off modes differ.

## Native import and comparative rollforward

The native TB intake format is `nxt-engagement-tb/v1`, with explicit account IDs, codes/names/kinds and current/prior cent columns. It is not a Caseware export format. Preview binds a saved revision and document and exposes proposed account rows plus reconciliation `checks` for inspection before commit. Commit applies that preview once. Existing local group mapping survives only for matching account ID and kind. A committed receipt retains preview ID, source/canonical hashes, provenance, input revision and timestamp in `import_history`; native package export preserves receipts. Preview expires after 30 minutes. An already committed preview replays its current record without another effect; it does not overwrite intervening work. Schema/reference errors fail visibly.

Rollforward is a **comparative working-paper copy from a locked, fresh supported source** into a later non-overlapping period: the new period gets prior balances derived from the source's adjusted workpaper. Current balances, adjustments, workpaper bodies/adjustment references, notes, snapshots and sign-offs are cleared; only open issues explicitly selected for carryforward remain. It does not post an opening Ledger journal, close income into retained earnings, migrate assessed tax carryforwards or reproduce every Caseware year-end balance basis. The source stays unchanged; repeating its destination period returns a conflict.

## HTTP contract

All routes are under `/api/engagements` and use the existing workspace bearer-key gate. Responses use `Cache-Control: no-store`; requests use strict schemas. Mutations require `expected_revision`, including calculation. Stale concurrent writes fail rather than overwrite a competing accepted revision.

| Route | Request/result responsibility |
| --- | --- |
| `GET /catalog`, `/summary` | Native schema/scope/readiness and aggregate status. |
| `GET /`, `POST /` | List engagements or create an `EngagementInput` draft. |
| `GET /{id}`, `PUT /{id}` | Full record or editable document replacement with `expected_revision`. |
| `POST /{id}/calculate` | `{expected_revision}`; reconcile the exact saved input and retain snapshot preimage/hashes. |
| `POST /{id}/signoffs` | `{expected_revision,workpaper_id,stage,operator,note}`, stage `prepared` or `reviewed`. |
| `POST /{id}/transition` | `{expected_revision,status,operator,note}`, requested state `draft`, `in_review`, `locked` or `archived`. |
| `POST /{id}/rollforward` | `{expected_revision,period_start,period_end,name?}`; new comparative draft. |
| `POST /{id}/import/preview` | `{expected_revision,document:{format:"nxt-engagement-tb/v1",accounts:[...]}}`. |
| `POST /{id}/import/commit` | `{preview_id,expected_revision}`; exact preview/retry-safe commit. |
| `POST /{id}/ledger/preview` | `{expected_revision}`; stage a bounded native Ledger capture, without posting books or committing the engagement import. |
| `POST /{id}/tax/preview` | `{expected_revision,jurisdiction:"AB"}`; locked, fresh 2025 engagement to selected-aggregate unconfirmed native T2 draft preview. |
| `POST /{id}/firm-proposal` | `{expected_revision,project_id?}`; idempotent Firm preparation-task proposal; human approval required. |
| `GET /{id}/package`, `/print` | Native JSON working-paper package or escaped printable internal workpaper. |
| `GET /audit` | Bounded operational/review audit; does not replace a statutory archive. |

An engagement record includes `id`, `revision`, `input_revision`, `status`, `document`, active `snapshot`, `snapshots`, current `signoffs`, `signoff_history`, `lock_history` and `import_history`. Each snapshot retains its exact `input_document` and result; review validates both hashes and the current saved input revision. Lists return bounded metadata, omitting documents and histories. Native packages preserve provenance; imported or model-generated text cannot establish an approved sign-off.

The input document contains `name`, `client_ref`, `kind`, current/prior period dates, `currency`, `accounts`, `groups`, `adjustments`, `workpapers`, `issues`, `notes` and optional `expected_revision`. Engagement classification (`internal`, `compilation`, `review`, `audit`) is metadata and confers no professional opinion or compliance claim.

Printable output includes saved account rows, trial-balance control totals, current/prior financial summaries, diagnostics, snapshot hashes and evidence/checkpoint text. Money is formatted from integer cents by the server. HTML escapes user content and carries a restrictive content-security policy; this is an internal workpaper, not a CaseView or professional financial-report export.

## Limits and operating boundaries

Current analysis bounds are 500 accounts, 200 groups, 200 adjustments, 100 workpapers and 200 issues; 100 lines per adjustment and 5,000 total lines. IDs allow 1â€“64 ASCII letters/digits/underscores/hyphens; codes are bounded nonblank text. Workpaper bodies and engagement notes are limited to 16 KiB each. Single monetary columns are nonnegative integer cents up to 100,000,000,000,000; aggregate arithmetic detects signed-64-bit overflow. HTTP bodies are limited to 1 MiB, input documents to 512 KiB, each saved record to 1 MiB and module state to 8 MiB, with at most 200 engagements. Per-record capacities are 20 calculation snapshots, 20 transitions, 2,000 sign-off history entries and 100 import receipts; capacity exhaustion returns a conflict instead of silently erasing that history. There are at most **40 import previews across the module, including committed previews retained for replay**; expired uncommitted previews are removed during later staging. This finite validation store needs an explicitly designed archival/capacity policy before sustained production intake. The rolling audit retains 1,000 events; queries default to 200 and allow at most 200 per page. These bounded stores are not a statutory long-term document archive.

Storage uses the selected native Store. Namespace separation isolates deployments, not companies or verified users. Existing shared-key limitations, backup scope, retention and migration NO-GO gates continue to apply. Source files, private attachments, identifiers, registration details, credentials and raw remote screenshots do not belong in source control.

## Rollforward origin archive

New comparative drafts retain an immutable `rollforward_origin`: source engagement/snapshot IDs, source input revision, exact input/output hashes, source/target dates, copy time, versioned copy policy and the full nonrecursive source calculation snapshot. The archived snapshot is evidence only. It does not become a current calculation or carry active approvals into the target. The archive includes prior source workpaper bodies and notes; clearing the new draft's fields does not erase historical evidence.

The target preserves account/group/workpaper structure and adjusted source balances as comparatives. Current balances, adjustments, workpaper bodies, notes and active calculation/review state are cleared. Only open issues marked for carryforward are copied. The source and external modules are unchanged. The original source snapshot remains available even after the source is reopened and edited. Duplicate destination protection uses immutable origin dates, so editing the target's ordinary period fields cannot authorize another copy for the original destination period.

Legacy records omit the optional archive without changing their existing input serialization/hash. Their historical origin is explicitly unavailable; it is not reconstructed from a possibly changed source. Existing 1 MiB record/8 MiB workspace limits apply to embedded evidence and reject an oversized operation before the CAS write. This bounded archive does not replace a scalable retention or company-isolation design. The UI exposes the new origin read-only in Output; JSON packages carry the complete archive. These are independently tested NXT provenance controls, not a claim of Caseware year-end-close parity.

## Text tickmarks and notes, implementation checkpoint

### Custom text catalogue, local implementation checkpoint

The next original NXT slice adds an engagement-local `tickmark_catalogue` of up to 50 definitions. Each definition has an ASCII ID, a 1â€“12 character uppercase ASCII code (letters, digits, underscores or hyphens), a nonempty label of at most 128 UTF-8 bytes and a nonempty single-line procedure description of at most 1,024 UTF-8 bytes. IDs and codes must be unique. `NOTE`, `AG`, `RC`, `TR`, `IN` and `CF` are reserved for NXT's fixed marks. These bounds and code choices are NXT policy, not recovered Caseware limits.

A `custom` annotation contains its own `custom_mark` definition copy. Editing or removing the current catalogue definition changes future choices; it does not rewrite an existing mark's meaning. Removed definitions may therefore remain in recorded annotation copies and history. Fixed annotations prohibit a custom definition. Empty catalogues and absent custom definitions are omitted from serialization to preserve legacy input preimages. Catalogue edits use the existing revision, review invalidation and lock controls. ## Opaque file versions

The Files & versions section preserves original bytes alongside an existing saved text workpaper. Each upload appends immutable metadata (filename, byte length, original-byte SHA-256, note, server-recorded time and unverified operator label), with request and version-metadata bindings. A caller-supplied upload ID and complete request binding make an exact retry return the existing result; reuse with changed fields is rejected. Generic document edits cannot inject, change or delete file history or remove an attached workpaper. Upload requires the current revision and an editable engagement, increments the input revision and invalidates active calculation and sign-offs. Locked and archived files remain downloadable.

Limits: nonempty files up to 256 KiB; 16 versions per workpaper; 128 distinct versions and 2 MiB total unique binary bytes per workspace. The existing 512 KiB input, 1 MiB engagement record and 8 MiB state limits also apply. Bytes deduplicate only within the same owner engagement and content hash; identical content cannot be appended again to the same paper. Exhaustion returns an error before atomic publication; there is no deletion, garbage collection or scalable attachment archive yet. Files are opaque: no preview, execution, editing, format interpretation or malware scan. Opening a downloaded file uses external software outside NXT's review boundary.

Routes beneath `/api/engagements` are `POST /{id}/workpapers/{paper}/attachments`, `GET /{id}/workpapers/{paper}/attachments/{version}`, and `GET /{id}/attachments/package`. Upload accepts `expected_revision`, `upload_id`, `file_name`, `operator_label`, `note` and lowercase `content_hex`. Downloads require existing workspace authentication and use attachment disposition, octet-stream, sandbox, no-store and nosniff. Browser original-file downloads independently check length and SHA-256 before creating an output; stale navigation responses are ignored. The upload modal reuses one request identity on unchanged retry and checks its engagement context after asynchronous file reads. Metadata is escaped and narrow displays wrap table content.

The existing JSON package adds an attachment manifest only when files are referenced; JSON does **not** contain file bytes. Download file bundle ZIP retains `engagement.json` and all unique referenced originals from current inputs, calculation history, active snapshot and the immutable rollforward origin. The deterministic store-only ZIP uses generated owner/hash paths rather than submitted filenames and is limited to 4 MiB. Rollforward clears active file refs in the new period, records that copy policy, and retains exact source refs/bytes in its archived origin. Later source uploads cannot change that origin bundle.

Blobs and metadata are kept in the existing atomic EngagementState KV and are covered by the existing three-table NXT Store backup scope. There is no new bucket, secret, table or permission grant. An older application that does not preserve these optional fields/root blobs is **not a safe rollback writer** after file intake; use a compatible reader and a tested forward fix or restore with a compatible binary. Hashes are unkeyed stored consistency references, not authenticated source attestations or independently verified authorship/time.
